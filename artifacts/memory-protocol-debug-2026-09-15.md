# GLM 记忆写入失败：定位与修复

日期：2026-09-15。范围：三事实输入的后台记忆协议、执行前约束和内容过滤。所有真实调用只发送脚本中的虚构数据，数据库均为临时数据库。

状态：DONE_WITH_CONCERNS。已捕获后台失败、完成针对性修复、通过失败回放和后台真实重测；端到端复查另发现一例前台 action 协议错误，未归为后台写入失败。

## 结论

发现并修复了三类实际失败：模型输出不符合 JSON 协议；SPLIT 缺少目标但直到执行才检查；中文禁止记忆规则把“分别记录”误判为“别记”。因此既有模型输出问题，也有实现契约和过滤边界问题，不是记忆架构本身没有作用。

最初那次历史失败没有保存原始响应，无法追溯它具体属于哪一种。但本轮对完全相同的输入已经再次捕获 `json_invalid`，并保存了原文。

## 证据

### 1. 原样输入：Schema 混入响应且缺少结束括号

原样输入：

> 请记住这三件事：我的自行车叫银杏；我的读书小组叫雾松；我最喜欢的棋类是围棋。

增加诊断、尚未改变生成或解析行为时，累计重测 39 次：38 次成功，第 39 次失败。该数字仅描述这批重测，不代表固定失败概率。

证据：`memory-protocol-original-capture-2026-09-15.json`，第 16 个 attempt（此前其他文件已有 23 次）。

响应开头是 `{"additionalProperties": false, "properties": ...`，模型将 Schema 字段用于实例输出，且最外层对象缺少结束括号。

具体错误：`Invalid JSON: EOF while parsing an object at line 3 column 0`。失败阶段为 `operation_validation`，类型为 `json_invalid`，未写入任何记忆。

修复：明确“Schema 是校验规则，不是输出模板”，仅输出实例字段；协议校验失败时最多重新生成一次，附带错误类别和原响应作为待校验数据。不会自动补括号、从残缺响应提取内容或放松来源校验。

### 2. 边界表述：JSON 后追加围栏或说明

边界输入在原三事实后明确要求“分别保存为独立记忆，方便以后单独纠正”。

证据：`memory-protocol-separate-after-2026-09-15.json` 的第 1、3 个 attempt。这个文件生成时只修复了中文过滤，尚未修复协议。

- 一条响应在合法 JSON 之后追加一行四个反引号。
- 另一条追加“``说明：用户明确触发记忆保存……”等正文。
- 均产生 `json_invalid`，具体原因为 `trailing characters`。

修复：仅移除响应最外侧的独立 Markdown 围栏行。说明文字、第二个对象、截断 JSON 仍然被拒绝，并最多触发一次重新生成。生成和校验响应都适用同一围栏处理规则。

### 3. JSON 合法，但误判“分别记录”为禁止记忆

证据：`memory-protocol-separate-before-2026-09-15.json` 第 2 个 attempt。

模型内容包含“**三条信息以 fragments 形式分别记录**”，实际旧规则 `别记` 匹配了“分**别记**录”，造成 `apply` 阶段失败：“记忆类别或内容不符合策略”。

修复：排除“分别记…”和“特别记…”的肯定语义词组，继续扫描文本中其他真正的禁止表达。“请分别记录，但这条别记”仍被禁止。

### 4. SPLIT 没有目标，协议仍放行

证据：`memory-protocol-final-original-2026-09-15.json` 第 1 个 attempt。该文件是补全目标约束前的中间验证，不是最终通过结果。

模型返回 `operation: SPLIT` 和三个 fragments，但没有已有记忆目标。这种操作的语义是拆分已有记忆，不能用于首次新增。旧 Schema 没有表达必须提供目标的要求；结果独立校验已消耗调用，执行阶段才返回“需要目标版本”。

修复：在 `MemoryOperation` 中提前验证需要目标的操作；增加 targets 字段说明。缺少目标返回 `memory_target_required`，进入同一个最多一次的重新生成流程。来源、锁定、有效性和版本匹配仍在执行阶段强制检查。

## 修改位置

- `calendar_agent/memory/jobs.py`：明确实例输出要求、一次协议重试、阶段/类型诊断、格式规范化记录。
- `calendar_agent/memory/operations.py`：仅清理外围围栏；需要目标的操作提前校验。
- `calendar_agent/memory/service.py`：修复“分别记录”“特别记住”误判。
- `tests/test_agent_refactor.py`：增加失败响应回放、严格拒绝、重试上限和来源检查回归。
- `scripts/probe_memory_protocol_live.py`：可复现的合成输入、原始输出、详细错误及可选新会话回忆。

普通成功路径仍是一次生成、按风险最多一次校验。只有协议失败时额外允许一次生成，因此每个后台作业最多三次模型调用。重试仍失败则保持失败，不写入。

应用诊断不保存完整原文或失败响应，只记录阶段、错误类型和字段位置；原始响应仅由本次专用合成测试脚本保存，并对疑似秘密内容整段遮蔽。

## 边界与后续

此修复不保证模型永远输出合法数据；二次生成仍不合格时继续失败关闭。最终真实样本规模小，不能据此承诺固定成功率。

最终发现的前台 action 错误已原样保留，当前合成脚本仅捕获后台原始响应，因此本轮没有据此断言前台到底缺失了 action 还是使用了非法枚举。前台协议修复需要单独捕获决策原文，不应通过再次运行成功就覆盖此失败。

当前多事实 ADD 仍会将三项内容保存在一条记忆里，未实现逐事实独立新增。冲突治理、前台保存反馈和遗忘粒度属于此前已知问题，本轮未扩展到这些机制。

## 持久排查记录

后台错误“JSON”原先只表示 Pydantic 错误位置在根节点，不能单凭这个词判定非法语法。必须保留错误类别。此次确认的语法失败包括 Schema 混入且截断、尾随围栏和尾随说明；合成原文可回放，生产诊断应避免落盘完整用户正文。
