# Agent 整体记忆功能测试

日期：2026-09-15。测试对象：运行时的 `/api/agent/runs`、记忆中心 API、后台巩固和真实本地 Embedding。

## 结论

基础长期记忆确实有效：两个模型都能跨新会话回忆、通过同义问法召回、使用纠正后的事实，并在用户忘记后停止复述。复杂场景仍存在可复现的流程问题：前台错误描述记忆能力、后台未发现较早的冲突事实、共享来源导致遗忘范围扩大。多事实写入在本轮 GLM 上失败，在 DeepSeek 上成功。

这是一次小样本功能审计，不是统计意义上的模型排名、架构收益证明或原创性评价。

## 测试方式与范围

- 原有确定性回归：`scripts/test_current.py`，76 项全部通过，耗时 22.340 秒。
- 真实模型：GLM、DeepSeek 各 12 个 Agent 回合，共 24 回合；未发生模型回退。
- 所有用户信息均由脚本虚构，所有应用写入均在临时 SQLite 数据库，未使用真实日历数据。
- 常规记忆从 Agent 接口输入，后台运行实际 `process_one()`，然后运行实际 `rebuild()`。没有用伪造的模型或向量替代真实测试。
- 后台调度器关闭，由脚本主动处理已排队任务以缩短等待。因此验证了后台处理逻辑，未验证真实 30 秒调度、15 分钟闲置触发和长期连续运行。
- 查询均使用新的 `session_key`，避免从同一会话历史中直接抄答案。
- 纠正和忘记走记忆中心 API。冲突场景的旧事实与 12 条干扰记录通过 API 预置，不计为自动提取成功。
- 保留期通过调用 `retain(now + 8 天)` 模拟；没有真的等待八天。
- 两项额外确定性检查与真实模型结果分开记录。
- 未进行浏览器操作、实际进程重启、新的天气或日历写入端到端测试。原有回归覆盖部分相关行为。
- 按完整回答和记忆状态人工核阅，不使用关键词命中率作为总成功率。合理询问用户可以通过测试，即使 Run 状态是 `waiting_for_user`。

## 关键发现与证据

### 1. 前台与后台对“是否能记住”的认识不一致

证据位置：JSON 中两模型的 `remember`、`consolidation`、`cross_session`。

GLM 声称“没有写入长期记忆的工具，因此无法永久保存”；DeepSeek 也称“它只会在本次对话中可见”。但两个后台作业都成功完成两次真实模型调用，随后新会话都准确回答“青苔灯塔”。

实现解释：`Runtime.submit()` 检测“记住/remember”后独立排队；前台工具列表只有 `search_memory`，提示未将后台作业状态作为明确的保存回执提供给模型。

影响：用户可能认为保存失败，或误将前台承诺当作持久化成功。需要区分“已接收、待整理、已保存、保存失败”，让回答基于实际状态。

### 2. 本轮 GLM 的多事实提取未通过协议校验

输入：`请记住这三件事：我的自行车叫银杏；我的读书小组叫雾松；我最喜欢的棋类是围棋。`

GLM 的 `multi_consolidation` 返回 `failed`，错误为“模型协议校验失败：JSON”，一次生成调用后没有任何目标记忆；`multi_read` 明确回答没有这些记录。

DeepSeek 对同样输入生成一条包含三项事实的记忆，并在新会话和模拟保留期清理后都答对。这里证明三项内容可保留，但不是三条可独立更新的原子记忆。

本轮未保存巩固生成器的原始输出，只保存结构化错误和操作结果。因此不能进一步断言是 JSON 语法、字段类型还是具体操作约束错误；需要捕获原始生成响应再做针对性诊断。本例各模型只运行一次，不能推导一般失败率。

### 3. 旧冲突事实未进入后台比较范围

预置“常住南京”，再写入 12 条无关记忆，把旧事实移出最新十条，随后从 Agent 输入“请记住：我的常住城市是苏州”。

两个后台都 ADD 了苏州，未停用南京，也未产生 CONFLICT 操作。后续查询两个模型都能识别矛盾。这说明“读取时能发现矛盾”和“写入时正确治理矛盾”是两回事。

GLM 前台甚至已经询问是否更新城市，但同一输入触发的后台作业仍然直接新增苏州。

实现解释：`jobs.py` 给生成器和校验器的 `existing` 都是 `service.list()[:10]`，没有为当前事实检索全库中的相关冲突项。后台排队也没有关联前台的待确认决策。

### 4. 遗忘的粒度大于用户选中的事实

把“自行车叫银杏”和“读书小组叫雾松”拆成两条记忆但共享一个来源，忘记前者后，后者也不再有效。

实现解释：`MemoryService.forget()` 将共享来源和派生关系都传播为遗忘目标。这是当前保守实现的直接结果，不是随机模型错误。

影响：能保证相关来源不再被重新提取，但可能删除用户仍希望保留的独立事实。若产品期望为“忘记整段来源”，界面应说明范围；若期望为“仅忘记选中事实”，需要更细粒度来源关联。

## 建议处理顺序

1. 统一前台保存反馈与后台作业状态，避免错误承诺和错误否认。
2. 巩固前检索相关旧事实，并让后台尊重待确认状态。
3. 保存脱敏后的模型协议失败诊断，补多事实输出的验证与修复路径。
4. 明确遗忘范围，再决定采用源级提示还是事实级传播。

修复后先用相同案例回归，再补不同表述、长历史、多个来源和重复运行。此次结果不支持继续增加记忆模块。
